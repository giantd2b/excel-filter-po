IRIS CRM - Message Sending Flow

Technical deep-dive into how messages flow from admin's device to customer's LINE/Facebook

1. System Architecture Overview

Mobile App / Dashboard (Client)

  • React Native (Expo) / React + Vite
  • Axios HTTP client with Firebase Auth
  • Socket.IO for real-time updates
  • Optimistic UI rendering
  • AsyncStorage for message cache

NestJS Backend (API Server)

  • MessagesController → MessagesService
  • Firebase Auth Guard (JWT verification)
  • Prisma ORM → PostgreSQL
  • Socket.IO Gateway (WebSocket)
  • Firebase Storage (media upload)

External Platforms

  • LINE Messaging API (Reply + Push)
  • Facebook Graph API (Send API)
  • Firebase Storage (file hosting)
  • Firestore (backup writes only)

2. Complete Message Flow (Step by Step)

Step 1: User Taps "Send"

The mobile app immediately creates an optimistic message and displays it in the chat. The message appears with opacity: 0.6 and a tiny spinner instead of a checkmark.

// ChatScreen.tsx - handleSend() const tempId = addOptimistic({ text: trimmed }); // Show instantly setText(''); // Clear input immediately // Then fire API call in background (non-blocking for UI) await api.post('/messages/send', { oduserId, docId, text, channel });
File: apps/mobile/src/screens/ChatScreen.tsx

Step 2: HTTP Request to Backend

Axios sends POST /api/messages/send with Firebase Auth token in the header. The request interceptor automatically attaches the JWT.

// api.ts - Request interceptor api.interceptors.request.use(async (config) => { const token = await getFreshToken(); // Firebase ID token config.headers.Authorization = `Bearer ${token}`; return config; }); // Request body: { oduserId: "U1234...", // LINE/FB user ID docId: "U1234__Line_IRIS", // Customer ID in our DB text: "สวัสดีค่ะ", // Message content channel: "Line_IRIS" // Which channel to send via }
File: apps/mobile/src/services/api.ts

Step 3: Backend Auth Guard

The FirebaseAuthGuard verifies the JWT token using Firebase Admin SDK. If invalid, returns 401 Unauthorized. If valid, attaches admin info to the request.

// FirebaseAuthGuard verifies token const decoded = await firebase.auth().verifyIdToken(token); // req.admin = { id, name, email, role }
File: apps/api/src/common/guards/auth.guard.ts

Step 4: MessagesService.sendMessage()

The core logic. Determines the channel type and builds the appropriate API call.

// messages.service.ts - sendMessage() const isLine = channel.startsWith('Line_'); const isFacebook = channel.startsWith('FB_'); if (isLine) { const messages = buildLineMessages(text, mediaType, mediaUrl); sendMethod = await sendLineMessage(oduserId, messages, channel); } else { await sendFacebookMessage(oduserId, text, mediaType, mediaUrl, channel); }
File: apps/api/src/modules/messages/messages.service.ts

Step 5a: LINE - Reply API vs Push API

For LINE, the system first tries the Reply API (free, requires a replyToken within 25 seconds of customer's last message). If the token is expired or unavailable, it falls back to the Push API (uses monthly quota).

// Try Reply API first (FREE) const cached = replyTokenCache.consume(userId); if (cached) { await axios.post('https://api.line.me/v2/bot/message/reply', { replyToken: cached.replyToken, messages: [{ type: 'text', text: 'สวัสดีค่ะ' }] }); return 'line_reply'; // FREE! } // Fallback: Push API (USES QUOTA) await axios.post('https://api.line.me/v2/bot/message/push', { to: userId, messages: [{ type: 'text', text: 'สวัสดีค่ะ' }] }); return 'line_push'; // COSTS QUOTA
File: apps/api/src/modules/messages/messages.service.ts (sendLineMessage)

Step 5b: Facebook - Send API

For Facebook, always uses the Graph API's Send endpoint. Media is sent as an attachment, text as a separate message.

// Send to Facebook await axios.post('https://graph.facebook.com/v18.0/me/messages', { recipient: { id: userId }, message: { text: 'สวัสดีค่ะ' } }, { params: { access_token: pageToken } });
File: apps/api/src/modules/messages/messages.service.ts (sendFacebookMessage)

Step 6: Save to Database

After sending (success or fail), the message is saved to PostgreSQL via Prisma in a transaction — both the message record and the customer's lastMessagePreview are updated atomically.

await prisma.$transaction([ // 1. Create message record prisma.message.create({ data: { id: 'out_1711089600000', customerId: docId, text: 'สวัสดีค่ะ', type: 'OUTGOING', sender: 'ADMIN', timestamp: BigInt(Date.now()), status: 'sent', // or 'failed' adminName: 'Siri Ketprasat', } }), // 2. Update customer's last message preview prisma.customer.update({ where: { id: docId }, data: { lastMessageAt: new Date(), lastMessagePreview: '[You] สวัสดีค่ะ', } }) ]);
File: apps/api/src/modules/messages/messages.service.ts

Step 7: Firestore Backup (Fire-and-Forget)

A copy is written to Firestore for legacy compatibility. This is non-blocking — the API doesn't wait for it to complete.

// Fire-and-forget: don't await Promise.all([ userRef.collection('messages').doc(messageId).set({...}), userRef.update({ lastmessagetime: timestamp }), ]).catch(() => {}); // Ignore failures

Step 8: WebSocket Broadcast

The backend emits two Socket.IO events to all connected clients (dashboard + other mobile devices):

// 1. New message event — updates chat window inboxGateway.emitNewMessage(docId, { id: messageId, text: 'สวัสดีค่ะ', type: 'outgoing', status: 'sent', timestamp: 1711089600000, }); // 2. Conversation updated — updates chat list sidebar inboxGateway.emitConversationUpdated({ id: docId, lastmessagetime: timestamp, lastMessagePreview: '[You] สวัสดีค่ะ', });
File: apps/api/src/modules/inbox-gateway/inbox-gateway.gateway.ts

Step 9: Client Receives WebSocket Event

The mobile app's useMessages hook receives the message:new event. It removes the optimistic message and replaces it with the real one (with server ID and confirmed status).

// useMessages.ts - WebSocket handler socket.on('message:new', (payload) => { setMessages((prev) => { // Remove optimistic message that matches this real one const cleaned = prev.filter((m) => { if (!m.id.startsWith('optimistic_')) return true; if (m.text === mapped.text) return false; // Match → remove return true; }); return [mapped, ...cleaned]; // Add real message }); });
File: apps/mobile/src/hooks/useMessages.ts

5. Image Sending Flow

1. Pick & Compress Image

User selects image(s) from gallery. Each image is compressed to 1200px width, 70% JPEG quality using expo-image-manipulator to reduce upload size.

2. Show Optimistic (Local URI)

The compressed local image URI (e.g., file:///cache/image.jpg) is shown immediately in the chat bubble before uploading.

3. Upload to Firebase Storage

POST /messages/upload — File is sent as multipart/form-data, saved to Firebase Storage bucket at chat-media/{docId}/{timestamp}.jpg, made public, and the URL is returned.

4. Send Image URL to Platform

The public Firebase URL is sent to LINE/Facebook. LINE uses type: 'image' with originalContentUrl. Facebook uses attachment.payload.url.

5. WebSocket Replaces Local URI

The real message arrives via WebSocket with the Firebase URL, replacing the optimistic message that was showing the local file URI.

ScenarioWhat Happens
LINE/FB API call failsMessage saved to DB with status: 'failed'. WebSocket broadcasts failed status. Bubble shows red !
Network timeout on mobileOptimistic message marked as failed. Alert shown to user.
Firebase Auth token expiredAxios interceptor auto-refreshes token and retries the request once.
Reply token expired (LINE)Silently falls back to Push API. No user-visible error.
Image upload failsAll pending optimistic images marked as failed. Alert shown.
FB sync creates duplicateDuplicate detection by text+timestamp (5s window) or mediaType+timestamp (10s window) prevents duplicates.
